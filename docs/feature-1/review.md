## Findings

### [Critical] PATCH /api/attendance/{id}/note の認可ルール未定義

- **該当箇所**: FR-4「メモ編集」/ API設計「新規: メモ編集」
- **問題**: メモ編集エンドポイントに対する認可要件が未定義。「誰が」「誰のレコードを」編集できるかが仕様に書かれていない。さらに、現在の SecurityConfig では `PATCH /api/attendance/{id}/note` が `anyRequest().denyAll()` にフォールバックし、全ユーザーが拒否される。
- **想定される影響**:
  - 認可ルールなしで実装すると、一般社員が他人のメモを書き換え可能になる（IDOR脆弱性）
  - SecurityConfig に追加し忘れると本機能がそもそも動作しない
- **推奨する決定・追記**:
  - 「本人のみ編集可能」「本人＋管理者が編集可能」のいずれかを明記
  - SecurityConfig への追加パス・ロール要件を仕様に含める
  - レコードの所有者チェック（`record.employee.id == authenticatedUser.id`）の要否を明記
- **確認質問**: メモの編集権限は本人のみか、管理者も他人のメモを編集できるか？

---

### [High] API 破壊的変更の移行方針が未定義

- **該当箇所**: API設計「変更: 出勤打刻」— "既存のクエリパラメータからボディに移動"
- **問題**: 仕様では `employeeId` を「クエリパラメータからリクエストボディに移動」と記載しているが、これは既存 API の破壊的変更。しかし、現状のバックエンド実装は既に `@RequestBody` で受け取っており（Red phase で先行実装済み）、一方フロントエンドは未だクエリパラメータで送信している。仕様はどちらの状態を「現状」としているのか曖昧。
- **想定される影響**: 実装者がバックエンドの互換対応（クエリパラメータのフォールバック）を入れるか入れないかで判断が分かれる。フロントエンドとバックエンドの同時デプロイが必要な場合、デプロイ順序の制約が発生する。
- **推奨する決定・追記**:
  - フロントエンドとバックエンドの同時リリースが前提か、段階的移行かを明記
  - 他のクライアント（外部連携、モバイル等）の有無を確認
  - 同時リリースなら「互換対応不要」と明記
- **確認質問**: 現在のフロントエンド以外にこの API を呼ぶクライアントは存在するか？

---

### [High] PATCH API の null/空文字のセマンティクスが曖昧

- **該当箇所**: API設計「新規: メモ編集」— "null は「変更しない」を意味する"
- **問題**: `null` が「変更しない」なら、既存のメモを「削除（空にする）」する方法がない。空文字 `""` がクリアを意味するのか、リクエストに含めないことが「変更しない」を意味するのか（JSON Merge Patch セマンティクス）、仕様が不明確。
- **想定される影響**: 実装者によって解釈が分かれ、「メモを消したいのに消せない」「意図せずメモが消える」のどちらかが発生する。
- **推奨する決定・追記**:
  - `null` = 変更しない、`""` (空文字) = クリア、フィールド省略 = 変更しない　のように3状態を明記
  - または JSON Merge Patch (RFC 7396) に準拠する旨を明記
- **確認質問**: ユーザーが一度入力したメモを完全に削除する操作は必要か？

---

### [High] 楽観ロック（@Version）未考慮

- **該当箇所**: FR-4「メモ編集」/ API設計「新規: メモ編集」
- **問題**: `AttendanceRecord` エンティティには `@Version` による楽観ロックが設定されているが、PATCH リクエストに `version` フィールドがない。本人が編集中に管理者が同じレコードを修正申請承認した場合、`OptimisticLockException` が発生するが、その処理が未定義。
- **想定される影響**: 並行編集時に 500 エラーが返り、ユーザーに適切なメッセージが出ない。リトライすれば成功するが、ユーザーが何をすべきかわからない。
- **推奨する決定・追記**:
  - PATCH リクエストに `version` を含めて 409 Conflict を返す方式にするか
  - メモ編集は last-write-wins（楽観ロック無視）でよいなら明記する
  - 「修正申請の承認」と「メモ編集」が同時に走った場合の優先順を決める

---

### [Medium] メモ入力欄の共有とクリアタイミング

- **該当箇所**: 画面設計「打刻画面」— メモ欄は1つ
- **問題**: 画面設計ではメモ入力欄が1つだけ配置されているが、出勤・退勤それぞれで別のメモを保存する。出勤後に「退勤メモ」を入力する際、出勤時に入力したメモの内容が見えるのか、クリア済みなのか。「打刻成功後にメモ欄をクリアする」とあるが、出勤打刻後にステータスが「勤務中」になった状態で退勤ボタンを押す前にメモを入力する想定と理解してよいか。
- **想定される影響**: ユーザーが退勤メモを入力しようとして、前の出勤メモが残っていて混乱する、あるいはクリアされていて退勤用に改めて入力が必要と気づかない。
- **推奨する決定・追記**:
  - 「打刻成功後にクリア」で十分か、placeholder テキストをステータスに応じて変更するか
  - 出勤済み状態での placeholder を「早退理由など（任意）」に変更するなど

---

### [Medium] チーム勤怠画面でのメモ閲覧範囲

- **該当箇所**: FR-3「メモ表示」— "チーム勤怠画面・全社員勤怠画面でもメモを確認できる"
- **問題**: 現在の SecurityConfig では `/api/attendance/team/**` は `authenticated()` で全認証ユーザーがアクセス可能。メモには遅刻理由・体調情報など個人的な内容が含まれうるが、「管理者全員が閲覧可能」とだけ書かれている。チーム勤怠 API を呼べる一般社員がメモも含めて見えてしまうのでは。
- **想定される影響**: 同僚の遅刻理由（「通院のため」など）が他の一般社員にも見える可能性。プライバシー上の問題。
- **推奨する決定・追記**:
  - チーム勤怠 API でメモを返すのは管理者のみに制限するか
  - それとも `/api/attendance/team` 自体のアクセス権限を見直すか
- **確認質問**: チーム勤怠画面は管理者専用か、チームメンバー全員が互いの勤怠を見られる仕様か？

---

### [Medium] メモの入力文字制限（改行・特殊文字）

- **該当箇所**: バリデーション — "最大200文字"
- **問題**: 文字数上限のみ定義されているが、改行の可否、制御文字、絵文字（マルチバイト、サロゲートペア）の扱いが未定義。テキストエリアは通常改行入力可能だが、一覧表示時に改行があるとレイアウトが崩れる。
- **想定される影響**: 改行入りメモが月次履歴テーブルの行高を崩す、絵文字で VARCHAR(200) を超過する（バイト数 vs 文字数）。
- **推奨する決定・追記**:
  - 改行を許可するか（許可する場合、表示時の改行処理）
  - DB カラムの200制限は「文字数」か「バイト数」か明記（PostgreSQL の VARCHAR は文字数）
  - 絵文字（4バイト文字）を許可するか

---

### [Medium] メモ編集の操作導線が未定義

- **該当箇所**: FR-4「メモ編集」/ 画面設計
- **問題**: 「打刻後でもメモを編集できる」とあるが、画面設計にメモ編集のUI（編集ボタン、編集ダイアログ等）が記載されていない。どの画面から編集するのか（当日の打刻記録? 月次履歴?）、インライン編集かモーダルかも未定義。
- **想定される影響**: 実装者の裁量でUIが決まり、UXの一貫性が損なわれる可能性。テスト観点も定まらない。
- **推奨する決定・追記**:
  - 編集可能な画面を特定する（当日の打刻記録のみ? 月次履歴からも?）
  - 編集UIの方式（インライン編集 / 編集アイコン→ダイアログ / 詳細画面遷移）

---

### [Low] トランケート長の未指定

- **該当箇所**: 画面設計「月次履歴テーブル」— "長い場合はトランケートし、ホバーで全文表示"
- **問題**: トランケートする文字数が未定義。また、モバイルやタッチデバイスではホバーが使えない。
- **推奨する決定・追記**: トランケート文字数（例: 30文字）を指定、タッチデバイスでの代替表示（タップで展開等）

---

### [Low] 監査ログ・変更履歴の明示的な除外判断

- **該当箇所**: 非機能要件 — "メモの入力履歴（変更ログ）は保持しない"
- **問題**: 明示的に除外しているのは良いが、「編集期限なし」と組み合わせると、過去のメモが証跡なく書き換えられる。労務管理上、打刻メモが勤怠実績の補足証跡として使われる場合、問題になりうる。
- **推奨する決定・追記**: 「打刻メモは法的証跡ではなく備忘録である」旨を明記するか、将来的に監査ログ追加の可能性がある旨を記載

## Acceptance criteria proposal

仕様から不足している受け入れ条件:

```gherkin
# 認可
Given 一般社員Aがログインしている
When 社員Bの打刻レコードのメモを編集しようとする
Then 403 Forbidden が返される

# メモクリア
Given 出勤メモが「電車遅延」と記録されている
When メモ編集で clockInNote を空文字に更新する
Then 出勤メモが空（null）になる

# 楽観ロック競合
Given 社員Aが打刻レコードを開いている
And 管理者が同じレコードの修正申請を承認した
When 社員Aがメモを編集して保存する
Then 競合エラーが返り、再読み込みを促すメッセージが表示される

# バリデーション（境界値）
Given メモ入力欄に200文字ちょうど入力している
When 打刻ボタンを押す
Then 正常に打刻され、200文字のメモが保存される

Given メモ入力欄に201文字入力している
When 打刻ボタンを押す
Then バリデーションエラーが表示され、打刻は実行されない

# 権限付きメモ表示
Given 一般社員がチーム勤怠画面を閲覧する
When 他の社員のメモカラムを確認する
Then メモが表示される / されない（要決定）
```
